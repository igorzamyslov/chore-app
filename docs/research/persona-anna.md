# Persona walkthrough: Anna, the organiser

*Research pass, 2026-08-07. Read-only — no files changed, no build/test/emulator run. Grounded in `docs/specs/{design-language,sync-backend,sync-freshness,onboarding-v2,occurrence-lifecycle,recurrence-engine,members-management,notifications,ui-foundation-chores,ui-shopping,ux-round-2,polish-round-1,data-layer}.md`, `docs/feedback/{2026-08-01-field-feedback,2026-08-01-ux-audit,2026-08-06-conventions-audit,2026-08-07-field-feedback}.md`, `docs/future-improvements.md`, and the widgets/services under `lib/`.*

Anna set Famdo up. She is the household's system-of-record: if it's not in the app, it didn't happen. She is optimising for two things above all else — **fairness she can verify** (who is actually doing the chores, is the rotation honest) and **agreement between her devices** (phone + old tablet, and now her partner's phone). She opens every Settings row on principle, edits things other people created, and will notice immediately if a number on screen disagrees with the list under it. Destructive or identity-changing actions should announce themselves; anything less is a small betrayal of the "this is the record" contract.

Per the brief, items already logged in `docs/future-improvements.md` or already decided in `docs/feedback/2026-08-07-field-feedback.md` are **not** re-reported as new findings below — they're noted briefly, once, as "already known" so the surface tables stay complete, and I flag the few places Anna's specific angle adds something those write-ups didn't say.

## Multi-device / multi-member

For every write (chore complete/skip/pause/delete/reopen; shopping add/check/edit/delete/clear; member add/rename/recolor/delete; category add/edit/reorder/delete; household rename): confirmed the same pattern everywhere — a plain repository write stamping `syncDirty: syncDirtyOnWrite` (`lib/data/db/sync_dirty.dart`), no per-feature special-casing (verified directly in `chore_repository.dart`, `shopping_repository.dart`, `member_service.dart`, `category_repository.dart`, `household_repository.dart`).

Propagation timing, from `lib/application/sync_engine.dart` + `docs/specs/sync-freshness.md` (already-known mechanism, confirmed live in code):
- The writing device: any write to a synced table schedules a debounced push (~2s, `pushDebounce`), which pushes then pulls on success.
- The other device: a healthy realtime subscription delivers the change and triggers a pull, typically sub-second (`sync_engine.dart:252-254`). If realtime is degraded in a way the resubscribe-tick can't catch, the 60s foreground safety poll bounds the staleness (`sync_engine.dart:290-301`); a manual pull-to-refresh (push-then-pull) is always available while linked.
- If the other device is **signed out but still linked**, none of the above runs at all — `syncEngineProvider` requires both linked *and* signed-in (`providers.dart:378-397`) — already-known (ux-audit A5 / field feedback 2026-08-07 A1).
- **Device-scoped settings never sync**: language, theme, digest time, and — critically for Anna — `actingMemberId` (`settings_repository.dart`, confirmed no `syncDirty` stamped on any of these writes). Each device keeps its own "who's currently using this phone."
- **`chore_assignees` removal doesn't propagate** (documented, `sync-backend.md` §8.5): removing a rotation member is a local hard delete with no tombstone, so a device that doesn't independently make the same edit never learns the member was removed — see Top Finding #10 for the concrete consequence to rotation fairness specifically.

## Top findings

Ranked by how much they undercut Anna's two priorities — verifiable fairness, and devices that agree.

1. **The day-progress card's count and the list under it can disagree, by design.** `ChoreProgressCard`'s `completedToday`/`pendingDueOrOverdue` are computed from the *unfiltered* occurrence lists (`chores_list_screen.dart:62-74`), while the sections below apply whatever member/category filter is active (`chores_list_screen.dart:353-391`) — a comment even says this is deliberate. So the moment Anna filters to "just my chores" to check her own load, the card at the top still reads "3 of 8 done today" for the whole household while the list beneath shows her own 1-of-2. This is exactly the "a number disagrees with the list" failure mode she is built to notice, and it happens on the single screen she opens most.

2. **Deleting a chore promises kept history with no way to ever see it.** The delete dialog says "Its history is kept, but its pending occurrence is removed" (`chore_delete_dialog.dart`), and that's technically true — `softDeleteChore` only hard-deletes the pending occurrence (`chore_repository.dart:232-249`). But every read path filters on the parent chore's `deletedAt IS NULL` (`watchActiveChores`, `watchClosedOnDate`, etc.), and there is no history or stats screen anywhere in the app (confirmed by grep — F19 "who actually does the chores" is still backlog). So "kept" means "kept in a table nothing will ever query again." For a user whose mental model is "if it's not in Famdo, it didn't happen," deleting a stale or duplicate chore quietly erases its contribution to a record she believes still exists — the same "promise without a mechanism" pattern already caught for the archive file (ux-audit A4), just not previously noticed for chore deletion itself.

3. **Backgrounding mid-magic-link on the old tablet drops her out of the join flow entirely.** The whole join wizard (email sent, waiting, chooser, "I'm new here") lives in plain widget `State` (`welcome_join_page.dart:51-64`) with nothing persisted. Anna's stated setup includes an "old tablet" — exactly the device most likely to have its background processes reaped while she switches to Mail to tap the link. On relaunch she's back at the two-card `WelcomeScreen`, signed in (the Supabase session survived) but with no memory of being mid-join; she has to notice this herself, tap "Join" again, and only then does the reconnect-or-code path pick up her signed-in state. The identical risk exists for the Settings-side join sheet on an existing install.

4. **Anyone can "become" another household member with one tap, and it doesn't sync — so her two devices can disagree about who's completing chores right now.** Two facts compound: the acting-member switcher is unconditionally shown regardless of whether the household is linked/signed-in (the "pin it, add Mark-done-for instead" fix is decided but not built — field feedback 2026-08-07 B1, confirmed absent by grep), and `actingMemberId` is a device-scoped `settings` row that never syncs (`settings_repository.dart` writes carry no `syncDirty`). Concretely: Anna's phone can be set to "acting as Anna" while her tablet — last touched by her kid — is still set to "acting as Dad." Any chore completed from the tablet credits Dad, silently, with zero confirmation and zero cross-device indication. This is the sharpest possible violation of "fairness she can verify," and it's worse on multi-device households than the single-phone framing B1 was written against.

5. **Rotation order can only be changed by deselect-then-reselect, which always re-appends at the end — there is no way to simply move someone.** Traced exactly: `_onMemberTap`'s rotation branch (`chore_form_screen.dart:409-424`) removes a re-tapped member and, on re-adding, always appends to the end of the list; there's no drag, no insert-at-position. To move member #2 ahead of member #1, Anna must deselect #1 and reselect it — which puts #1 *last*, not first. The Categories screen right next to this one has full drag-to-reorder (`manage_categories_screen.dart`), so the asymmetry is exactly the kind of thing she'd notice and be unable to explain.

6. **A claimed member or the household's last member gets a Delete button that simply vanishes, with no explanation.** `_canDelete` (`member_edit_sheet.dart:79-86`) correctly gates the button, but when it's `false` nothing takes its place — no disabled state, no "can't remove the last person" text, no "this profile is linked to an account" note. Anna, who opens every settings row and expects an explanation for anything she can't do, hits a quiet dead end exactly where the (already-fixed) A1 audit item told her deletion would now work.

7. **Deleting a category never says how many chores or items will lose it.** The confirm dialog says "Chores and items using it become uncategorized" but there's no count anywhere in the flow (`category_edit_sheet.dart`, `category_delete_dialog.dart`) — no "3 chores and 5 items" before she commits. For someone who tracks assignments precisely, an unqualified "some things will change" before an irreversible action is the wrong side of her risk tolerance, even though the action itself (soft delete, becomes uncategorized rather than broken) is safe.

8. **The only way to unlink a device from its household is to destroy every local row on it.** Confirmed by exhaustive grep: no "Disconnect" affordance exists anywhere; the sole path that clears `syncHouseholdId` is the full double-confirmed Reset, which deletes members/chores/shopping items on that phone (the household survives server-side, but this phone's working copy doesn't). This is already decided and queued (field feedback 2026-08-07 A1.2) — flagged here at extra weight because it's the exact kind of irreversible-without-warning gap Anna's mental model treats as a broken promise: "disconnect" should not require "destroy."

9. **The daily digest can't tell her chores from anyone else's.** `dueTodayCount`/`overdueCount` are summed across every pending occurrence in the household regardless of `assignedMemberId` (`providers.dart:736-745`). On a synced household where she and her partner both enable the digest, both phones fire the identical count every morning — neither says "1 of those is yours." This sits adjacent to, but is more specific than, the backlogged F16 ("finer-grained notifications") — it's not about frequency or per-chore reminders, it's that the one notification that exists isn't even scoped to the person receiving it.

10. **Removing a member from a chore's rotation on one device doesn't propagate to the other — so the removed person keeps getting turns wherever no one makes the same edit.** This is the concrete, personal-scale consequence of the already-documented `chore_assignees` tombstone gap (`sync-backend.md` §8.5): the local removal is a hard delete with no dirty flag to push, so it never reaches the other device. If Anna removes her teenager from the dish rotation on her phone (say, they moved out), her partner's phone keeps computing `nextRotationAssignee` against its own stale, still-including-them local copy — the person she explicitly removed can still be assigned turns on the other device until someone happens to make a different full edit to that chore's assignee list there too. The spec calls the general limitation out; the fairness-specific bite of it is new.

## Things that pleasantly surprised her

- **Editing recurrence or the start date on an existing chore now correctly regenerates the pending occurrence** (two-floors rule, same as unpause; assignee re-resolved the same way) — a real fix, not the "known v1 simplification" an older spec comment still describes. Anna edits things other people set up; this used to silently go stale.
- **The unsaved-changes guard on the chore form is a real snapshot diff**, not a blunt "any keystroke = dirty": toggling repeat on and back off without changing anything doesn't trip it, but every meaningful field does, and the discard dialog defaults to "keep editing."
- **Reopen's LIFO restriction is enforced at both the service and the UI layer** — the Done-today section computes each chore's true latest closed-today row from the *unfiltered* list specifically so an active filter can never offer a Reopen that would throw. A quietly careful piece of engineering.
- **Resume from background is one observer doing three correct things**: catch-up, digest recompute, and sync push/pull, all triggered together, with the sync engine's 60s poll specifically paused while backgrounded so it isn't a battery drain.
- **The realtime-gap fix is exactly targeted**: a (re)subscribe tick — not just a live event — triggers a pull, which is precisely what closes "my phone dropped Wi-Fi for ten minutes and never noticed it missed anything."
- Several items from the two most recent audits are already fully shipped, not just decided: the filtered-empty state, add-member-inline and add-category-inline, household rename, invite revoke-on-recreate, reconnect-before-adopt/join, "Last synced," pull-to-refresh on both lists with a hand-tuned displacement, the tab-bar ripple fix, and the shopping suggestion `ValueKey` fix. The backlog documents read as aspirational in places, but a real fraction of it is already live.
